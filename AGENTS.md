# I. Состояние проекта

## 1. Сущность проекта

**GitPlus** — CLI-утилита для автоматизации типового цикла коммита в Git-репозитории.

Проект ориентирован на:

- автоматическое добавление изменённых и новых файлов в индекс;
- управление версией через файл `VERSION`;
- формирование сообщения коммита из аргументов командной строки или из `CHANGELOG.md`.

Основная ценность проекта — в согласованности между:

- логикой скрипта `gitplus.py`;
- форматом `CHANGELOG.md`;
- файлом `VERSION`;
- кодом;
- документацией.

Проект представляет собой единый самодостаточный скрипт с сопроводительными файлами. Это допустимое исключение из правила «код в `src/`».

## 2. Топология проекта

Проект имеет плоскую структуру без `src/`, `tests/`, `docs/` и других стандартных каталогов:

```text
VERSION
CHANGELOG.md
AGENTS.md
README.md
gitplus.py
```

Это простой однофайловый инструмент, и усложнение структуры не требуется без прямого указания пользователя.

## 3. Назначение файлов

### `gitplus.py`

Основной и единственный исполняемый модуль проекта.

Содержит два сценария работы:

* **Сценарий (a) — быстрый коммит**: активируется при передаче аргумента командной строки или при отсутствии блока `[Unreleased]` в `CHANGELOG.md`. Инкрементирует версию, формирует сообщение коммита из аргумента.
* **Сценарий (b) — коммит через Changelog**: активируется при наличии блока `[Unreleased]` в `CHANGELOG.md`. Извлекает версию и тело сообщения из changelog, снимает метку `[Unreleased]`, обновляет `VERSION`.

### `VERSION`

Текущая версия проекта. Управляется скриптом `gitplus.py` при коммите.

### `CHANGELOG.md`

История изменений проекта. Служит буфером передачи ответственности от агента к пользователю и далее к `git+`.

### `README.md`

Пользовательская документация: описание, сценарии использования, требования.

## 4. Источники истины

| Область              | Источник истины                              |
| -------------------- | -------------------------------------------- |
| Логика работы        | `gitplus.py`                                 |
| Публичный интерфейс  | `README.md`                                  |
| История изменений    | `CHANGELOG.md`, git log                      |
| Текущая версия       | `VERSION`                                    |
| Правила для агента   | `AGENTS.md`                                  |

Если код и источник истины расходятся, агент не должен молча выбирать код как более актуальный.

Агент должен явно сообщить о расхождении и предложить одно из действий:

* привести код к документации;
* обновить документацию под фактическое поведение;
* зафиксировать вопрос для решения пользователем.

## 5. Архитектурные инварианты

Агент обязан сохранять следующие инварианты:

* `gitplus.py` остаётся единым самодостаточным скриптом;
* два сценария (a) и (b) сохраняют свою логику переключения;
* формат заголовка changelog `## X.Y.Z [YYYY-MM-DD HH:MM:SS] [Unreleased]` не меняется без согласования;
* формат сообщения коммита сценария (a) `X.Y.Z [YYYY-MM-DD HH:MM:SS]: message` не меняется без согласования;
* зависимость только от `GitPython` и стандартной библиотеки;
* публичные контракты не меняются без обновления `README.md`.

## 6. Антипаттерны

Запрещено:

* создавать временные скрипты или промежуточные планы в корне проекта;
* молча игнорировать расхождение между `README.md` и `gitplus.py`;
* подменять архитектурное решение локальным хаком;
* менять `VERSION` без прямого разрешения пользователя;
* выполнять git-команды изменения без прямого разрешения пользователя;
* ломать совместимость формата `CHANGELOG.md` с парсером в `gitplus.py`;
* добавлять внешние зависимости без согласования.

# II. История проекта

## 7. VERSION

Файл `VERSION` содержит текущую версию проекта.

Агент не меняет и не инкрементирует `VERSION`.

Исключение возможно только при прямом, недвусмысленном указании пользователя.

## 8. CHANGELOG.md

Все изменения агента должны быть отражены в `CHANGELOG.md`.

`CHANGELOG.md` — это буфер передачи ответственности от агента к пользователю и далее к `git+`.

Агент отвечает за содержательное описание изменения в блоке `[Unreleased]`.
Пользователь отвечает за ревью diff и закрытие изменения в git-историю.

### 8.1. Проверка `[Unreleased]`

Перед завершением задачи агент обязан проверить, есть ли в `CHANGELOG.md` блок с меткой `[Unreleased]`.

Если блок существует, агент добавляет запись в подходящую секцию этого блока.

Если блока нет, агент создаёт новый блок над последним существующим блоком.

### 8.2. Создание нового блока

При создании нового блока агент:

1. читает текущую версию из `VERSION`;
2. инкрементирует patch-часть только в заголовке changelog;
3. не меняет файл `VERSION`;
4. создаёт заголовок:

```markdown
## X.Y.Z [YYYY-MM-DD HH:MM:SS] [Unreleased]
```

### 8.3. Секции changelog

Проект использует русскоязычные секции:

```markdown
### Добавлено

### Изменено

### Исправлено

### Удалено
```

Агент должен сохранять существующий стиль файла.

### 8.4. Требование к записи

Запись в `CHANGELOG.md` должна быть достаточно содержательной, чтобы пользователь понял смысл изменения без чтения полного diff.

## 9. Git-дисциплина

Git используется агентом только как инструмент наблюдения.

Разрешены read-only команды:

```bash
git status
git diff
git diff --staged
git log
git show
git blame
git rev-parse HEAD
git branch --show-current
```

Запрещены команды, изменяющие рабочее дерево, индекс, ветки, теги, историю или удалённые репозитории:

```bash
git add
git commit
git restore
git checkout
git switch
git reset
git revert
git merge
git rebase
git cherry-pick
git tag
git stash
git push
git pull
git fetch
```

Исключение возможно только по прямому, недвусмысленному приказу пользователя.

Даже если пользователь использует `git+`, агент не запускает `git+` самостоятельно, если пользователь явно не приказал это сделать.

## 10. GitPlus-контракт

Проект использует GitPlus-идеологию:

1. Агент готовит изменение.
2. Агент описывает изменение в `CHANGELOG.md` под `[Unreleased]`.
3. Пользователь смотрит diff в VSCode или другом инструменте.
4. Пользователь принимает, корректирует или отклоняет изменение.
5. Пользователь запускает команду `git+`.
6. `git+` обновляет `VERSION`, снимает `[Unreleased]` и создаёт унифицированный commit.

Агент не должен нарушать этот контракт.

# III. Правила разработки

## 11. Общий рабочий цикл агента

Перед изменением проекта агент должен:

1. прочитать `AGENTS.md`;
2. определить, какие источники истины относятся к задаче;
3. проверить текущее состояние файлов;
4. при необходимости посмотреть `git status` и `git diff`.

Во время изменения агент должен:

1. вносить минимальное связное изменение;
2. не смешивать независимые задачи без необходимости;
3. поддерживать синхронность кода и документации.

После изменения агент должен:

1. обновить `CHANGELOG.md`;
2. сообщить пользователю итог;
3. остановиться, не выполняя commit.

## 12. Минимальное связное изменение

```text
одна цель → один связный набор правок → одна запись в CHANGELOG.md
```

## 13. Правила зависимостей

* единственная внешняя зависимость — `GitPython`;
* импорты стандартной библиотеки: `os`, `sys`, `re`, `datetime`;
* новые внешние зависимости не добавляются без согласования с пользователем.

## 14. Документация и синхронизация

Если изменение затрагивает логику работы сценариев, формат changelog, формат сообщения коммита или публичный интерфейс, агент обязан обновить `README.md`.

```text
код изменил смысл → README должен быть проверен
код изменил контракт → README должен быть обновлён
код выявил расхождение с README → пользователь должен быть уведомлён
```

## 15. Финальный отчёт агента

После завершения задачи агент обязан сообщить пользователю итог.

Для тривиальных задач достаточно краткого итога и обновления `CHANGELOG.md`.

Для содержательных задач отчёт должен включать:

1. какие файлы изменены и что именно изменено;
2. какие источники истины были проверены;
3. обнаруженные расхождения между кодом и документацией;
4. что добавлено в `CHANGELOG.md`;
5. риски или нерешённые вопросы.

Агент не должен предлагать выполнить commit самостоятельно.

# IV. Пайплайн изменений проекта для LLM

1. Руководствоваться `AGENTS.md`.
2. Найти релевантную область проекта:
   * `gitplus.py`;
   * `README.md`;
   * `CHANGELOG.md`;
   * `VERSION`.
3. Проверить текущее состояние файлов.
4. Выполнить минимальное изменение.
5. Обновить `README.md` и `CHANGELOG.md` в соответствии с изменением.
6. Дать пользователю итоговый отчёт.
7. Остановиться без commit.

# V. Краткая формула проекта

GitPlus — это согласованный CLI-инструмент с контрактом на формат changelog и версионирования.

Агент должен поддерживать одновременно:

* корректность кода `gitplus.py`;
* согласованность с `README.md`;
* наблюдаемость изменений через `CHANGELOG.md`;
* пользовательский контроль над историей проекта через `git+`.
